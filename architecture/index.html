Engineering case study

Building a DAW as an open Rust ecosystem

How Maolan separates a real-time audio engine, desktop application, plugin runtime, reusable interface components, and neural audio research across focused repositories.

Reusable core

An engine, not just an application

The audio engine is independently consumable, with optional audio-file, MIDI-file, plugin, and control-surface capabilities.

Contained failures

One process per plugin

Third-party plugin code runs outside the DAW process, allowing a failed host to be bypassed without taking down the session.

Focused evolution

Independent repositories

Platform adapters, user-interface components, plugins, documentation, and AI research can change at different rates.

The problem

A DAW is several hard systems at once

The challenge is not only drawing a timeline or playing samples. It is keeping several incompatible rates of change and failure modes inside one coherent product.

Real-time deadlines

Audio processing must keep up with the hardware callback while recording, playback, routing, automation, and plugin processing compete for the same time budget.

Untrusted extension code

A DAW depends on third-party plugins, but a plugin crash or hang must not become a project crash. Supporting several formats adds more implementation and user-interface differences.

Platform diversity

ALSA, JACK, OSS, CoreAudio, WASAPI, and ASIO expose different audio models. Window embedding, MIDI, shared memory, and process synchronization add further platform-specific work.

Different rates of change

A stable audio callback, a rapidly evolving editor, packaging rules, and experimental neural models should not be forced into the same development and release cycle.

Maolan’s answer is to give each boundary a specific job: crates provide reuse, processes contain plugin failures, and repositories separate independent areas of development.

The architecture

Layered around ownership and failure

The main application owns project state and the workspace. The engine owns audio processing. Plugin hosts own third-party plugin instances, while a shared protocol defines their communication.

Runtime path

Application and project state

maolan contains the iced desktop application, workspace, command-line tools, session handling, and the thin plugin-host executable. It communicates with the engine through an asynchronous message channel rather than merging interface and DSP responsibilities.

Audio and routing

engine provides real-time audio and MIDI tracks, timeline playback and recording, routing, offline rendering, hardware backends, and plugin wrappers. Its Cargo features let consumers opt into file codecs, Standard MIDI File I/O, plugins, and MixOSC integration.

Shared plugin contract

plugin-protocol is the common contract between engine and host. plugin-host supplies the reusable format loaders, scanner, and runtime used by the executable.

Key engineering decisions

Choose explicit tradeoffs

01 / Plugin isolation

Move third-party code out of the DAW process

Every plugin instance receives its own host process. Audio buffers, parameter changes, MIDI, and transport data use shared memory; lightweight events coordinate the two sides. Single-producer/single-consumer ring buffers provide lock-free event queues.

If a plugin crashes, the operating system terminates only its host. The DAW can detect the failure, bypass the instance, and continue playback. This is an architectural guarantee about the failure domain, not a claim that every plugin is compatible.

The cost

Process creation, shared-memory ownership, synchronization, recovery, and cross-platform event handling are more complex than an in-process function call.

The constraint

The DAW and host must use compatible protocol versions. Fixed shared-memory layouts make protocol changes a coordinated release concern.

CLAP

The clap crate supplies API bindings, while plugin-host provides host extensions and the isolated runtime. Maolan’s own plugin collection also uses CLAP.

VST3

VST3 bindings and hosting live in plugin-host and use the same shared-memory protocol, event exchange, and crash-isolation path as the other formats.

LV2

The pure-Rust lv2 crate handles discovery and loading on Unix without a system lilv dependency, with hosting isolated in plugin-host.

Audio Unit

On macOS, plugin-host discovers Audio Units through the system registry and hosts both AUv2 and AUv3 components behind a common interface.

02 / Reuse

Keep the engine and widgets independently useful

The engine has no mandatory GUI dependency, and its default feature set is deliberately small. Applications can enable only the capabilities they need. The editor reuses shared audio decode and encode paths instead of growing a second media stack.

The widgets crate follows a similar rule: it supplies clip rendering, piano-roll surfaces, controls, meters, scrollbars, and MIDI data types, while higher-level editing behavior stays in the application. Pure layout and interaction logic can therefore be tested without launching the full DAW.

The benefit

The engine can serve other Rust applications, and multiple frontends can share media and interface infrastructure.

The cost

Public APIs, feature combinations, cross-crate patches, and publication order require deliberate maintenance.

03 / Native integration

Isolate unavoidable platform and FFI complexity

Platform backends keep ALSA, JACK, OSS, CoreAudio, WASAPI, and pure-Rust ASIO support behind the engine. LV2 discovery and loading use a pure-Rust implementation rather than a system lilv dependency. Audio import and export use Rust codec libraries, avoiding an FFmpeg dependency.

Rust does not remove the difficult parts: plugin ABIs, shared memory, operating-system events, window embedding, and audio APIs still require carefully scoped unsafe code. Portable SIMD and parallel processing help hot paths while retaining platform fallbacks.

The benefit

Most product logic stays separate from operating-system details, and codec or plugin support does not require a large external C multimedia stack.

The cost

Each backend and format needs its own validation. Memory safety at an FFI boundary depends on invariants that the Rust compiler cannot check automatically.

04 / Neural audio

Let research evolve beside the real-time core

The generation, Llama, pitch, training, and voice-conversion repositories form a separate research layer. Burn provides model execution, while model artifacts use formats such as BurnPack and safetensors and are downloaded or supplied locally rather than embedded in source repositories.

This separation makes hardware and asset requirements explicit. For example, the pitch crate’s FCPE detection and PC-NSF-HiFiGAN resynthesis require a working Vulkan GPU and have no CPU fallback. Model weights also carry their own licenses, distinct from the Rust source code.

The benefit

Model architectures and inference tools can change without redefining the engine’s real-time interfaces.

The cost

GPU availability, large downloads, conversion tooling, and per-model licensing become part of the user and release experience.

Delivery model

Independent crates, coordinated changes

There is intentionally no single Cargo workspace at the repository root. Each major component owns its manifest, lockfile, tests, and Git history; the main DAW has its own smaller workspace.

That structure supports focused development, but it does not remove integration work. Local path dependencies and patches connect sibling crates during development. Cross-cutting protocol or API changes still require checking dependents and coordinating publication.

Outcomes & lessons

Modularity is a product feature

The clearest results are visible in the system’s structure: reusable components, contained failures, and room for specialized tools without turning the DAW into a monolith.

Reuse beyond the GUI

The engine, plugin host, protocol, and widgets are available as focused building blocks rather than existing only inside the desktop binary.

A defined plugin failure domain

The process boundary turns a whole-application crash risk into a host-recovery problem that the engine can handle.

Specialization without duplication

The editor, player, plugins, and research tools can focus on their own jobs while sharing selected audio and UI infrastructure.

Tradeoffs stay visible

Version coordination, platform testing, unsafe boundaries, and model requirements are documented instead of hidden behind the word “modular.”

What the architecture teaches

  • Separate components according to ownership and failure, not just source-code size.
  • Put shared protocols in their own crate when two processes must agree on memory.
  • Make optional capabilities visible through explicit feature flags.
  • Treat release coordination and hardware requirements as part of architecture.

What remains hard

  • Plugin compatibility still varies by plugin, host behavior, and operating system.
  • Protocol changes require compatible DAW and plugin-host deployments.
  • Every native backend and plugin UI path needs platform-specific testing.
  • Maolan remains under active development; interfaces and behavior continue to evolve.

Conclusion

An open audio stack, built in layers

Maolan shows how a digital audio workstation can be decomposed without losing a coherent product: a reusable engine at the center, isolated plugin processes at the extension boundary, shared widgets across applications, and independent repositories for platform and research work.

The result is not a claim of finished software or universal plugin compatibility. It is an inspectable, actively evolving architecture whose main constraints—and the reasons for them—are visible in the source.
